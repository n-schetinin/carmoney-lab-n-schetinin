## Тесты

Все новые — в `tests/Unit/AssessmentServiceTest.php`. Зоны LTV — по фикстурам
спеки (`docs/spec/spec_MILEAGE.md`, раздел «Критерии приёмки»):
`payload(450000, 900000)` → LTV 50 (approve-зона), `payload(675000, 900000)` →
LTV 75 (review-зона), `payload(855000, 900000)` → LTV 95 (reject-зона). По тесту
на случай, имя — по поведению. В скобках — трассировка на критерии приёмки спеки.

Поведение нового правила:

- 399999 км, LTV 50 → `approve`, `approved_limit` = 450000 — порог не сработал (AC-MILEAGE-01).
- 400000 км, LTV 50 → `approve`, `approved_limit` = 450000 — ровно на пороге правило не срабатывает (AC-MILEAGE-02).
- 400001 км, LTV 50 → `review`, `approved_limit` = 0 — перезапись `approve` (AC-MILEAGE-03).
- 399999 км, LTV 95 → `reject`, `approved_limit` = 0 — при пробеге в норме решение как по LTV (AC-MILEAGE-05).
- 400001 км, LTV 95 → `review`, `approved_limit` = 0 — перезапись `reject`, выбор заказчика (AC-MILEAGE-04, REQ-MILEAGE-04).
- 400000 км, LTV 75 → `review`, `approved_limit` = 0 — граница правила в третьей зоне LTV: решение как по LTV, без влияния правила (AC-MILEAGE-06).
- 500000 км, LTV 50 → `review`, `approved_limit` = 0 — верхняя граница зоны действия правила, заявка до решения дошла (AC-MILEAGE-07).

Неизменный ввод пробега. Спека передала покрытие AC-MILEAGE-06, 08–10, 12–13
плану («чем их покрывать — существующими тестами или расширением списка в
плане»). Существующими тестами покрывать нельзя: в `ApplicationValidatorTest`
кейсов по `mileage` нет вообще, в `AssessmentServiceTest` — только 96 000 км.
Поэтому добавляем, все — через `assess()`, ожидание `ValidationException` с
ключом `mileage` в `errors()` (исключение в `assess()` до расчёта = решение
не вычислялось):

- 0 км, LTV 50 → `approve`, `approved_limit` = 450000 — нижняя граница диапазона валидна, доходит до решения (AC-MILEAGE-09).
- −1 км → `ValidationException` с `mileage` — ниже нижней границы, тот же код-путь, что у отсутствующего поля (AC-MILEAGE-10).
- 500001 км → `ValidationException` с `mileage` — потолок валидации не понижен (AC-MILEAGE-08). Регрессионная защита главного риска плана: если валидатор «выровняют» под 400 000, покраснеет первым этот тест.
- Ключ `mileage` отсутствует и отдельно `mileage` = `null` — оба случая, один код-путь `?? -1` (`ApplicationValidator.php:43`) → `ValidationException` с `mileage` (AC-MILEAGE-11). Пустой пробег — ошибка валидации (422), а не `review`.

## Риски

- **Столкновение с `max_mileage_km`.** В секции `vehicle` окажутся два mileage-порога с разной семантикой: 500 000 — потолок *валидации* (нарушение → 422, заявка вообще не доходит до решения), 400 000 — порог *решения* (> порога → `review`). Главный риск реализации — «выровнять» валидатор под 400 000: тогда заявки 400 001–500 000 начнут получать 422 вместо `review`, зона действия правила исчезнет, сломается сообщение валидатора и его тесты. `max_mileage_km` и проверка `ApplicationValidator.php:43–46` не меняются вообще.
- **Перезапись `reject` → `review` смягчает решение.** При пробеге выше порога отказ по LTV превращается в ручной разбор. Это зафиксировано заказчиком (интервью, вопрос 1; REQ-MILEAGE-04, AC-MILEAGE-04) — перезапись безусловная, альтернатива «`reject` важнее» снята с обсуждения. Риск реализации — пересоблазн «сделать как безопаснее» и понижать только `approve`: условие в шаге 3 перезаписывает любой вердикт; тест AC-MILEAGE-04 это ловит.
- **Смена сигнатуры конструктора `AssessmentService`.** Мест создания ровно два: `AppFactory.php:30` и `AssessmentServiceTest.php:24` (проверено поиском). Забыть `AppFactory` — runtime-ошибка на всех эндпоинтах; забыть `setUp()` — красный unit-сьют.
- **Границы.** «Не больше 400 000» реализовано строгим `>`: ровно 400 000 не срабатывает, зона действия 400 001–500 000. Граница зафиксирована заказчиком (интервью, вопрос 2; REQ-MILEAGE-01). Риск реализации — перепутать знак (`>=` вместо `>`); ловится тестами AC-MILEAGE-02/03/06.
- **`approved_limit`.** Правило никогда не даёт `approve`, поэтому при срабатывании лимит = 0 за счёт существующей логики; риск — случайно добавить свой расчёт лимита.
- **Сохранённые заявки.** Решение считается только в момент `assess()`; уже сохранённые заявки (включая seed) не пересчитываются — список и карточка продолжат отдавать старые решения. Для seed-заявок с пробегом 400 001–500 000 это расхождение с новым правилом, оно осознанное.
- **Соседнее, но чужое:** расхождение комментария и кода по границе `approve` (`<` vs `<=`, `DecisionEngine.php:10/32`) и справочник `ltv_by_age` (задача LOAN-12) — в задачу не входят, не трогать.
- **Пороги, лимиты и формулы не меняются ради зелёного `make test`** — при таком конфликте стоп и вопрос человеку (AGENTS.md).

Не входит в задачу: расчёт лимита по `ltv_by_age` (LOAN-12); фронтенд (форма уже
шлёт `mileage`, решение рендерится из ответа API); БД (`schema.sql`, `seed.sql`),
репозиторий и контроллер (контракт ответа не меняется: `decision` остаётся одной
из трёх строк); причины `review` в ответе API; пересчёт решений существующих
заявок; feature-тесты; изменение `max_mileage_km` и порогов LTV.
