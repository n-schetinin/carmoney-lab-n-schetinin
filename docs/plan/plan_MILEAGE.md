## Тесты

Все новые — в `tests/Unit/AssessmentServiceTest.php`; LTV-зоны берутся как в
существующих тестах (`payload(450000, 900000)` → LTV 50 = approve-зона,
`payload(855000, 900000)` → LTV 95 = reject-зона). По тесту на случай, имя — по
поведению.

- 399999 км, LTV 50 → `approve`, `approved_limit` = запрошенной сумме (порог не сработал).
- 400000 км, LTV 50 → `approve` (граница «не больше» — допустимо, срабатывает строгое `>`).
- 400001 км, LTV 50 → `review`, `approved_limit` = 0 (правило перебивает LTV-решение).
- 399999 км, LTV 95 → `reject` сохраняется — при пробеге в норме правило не трогает решение.
- 400001 км, LTV 95 → `review` — буквальная перезапись `reject` → `review`; тест закрепляет ответ на открытый вопрос №1 и меняется вместе с условием, если заказчик решит «reject важнее».
- 500000 км (потолок валидации), LTV 50 → `review` — правило срабатывает на верхней границе валидного диапазона 400 001–500 000.
- пустой пробег (ключ `mileage` отсутствует; `null` даёт тот же путь через `?? -1` в `ApplicationValidator.php:43`) → `ValidationException` с ошибкой по полю `mileage`, LTV и решение не вычисляются. Тест фиксирует: пустой пробег = ошибка валидации (422), а не `review`.

Существующие тесты (`DecisionEngineTest`, `ApplicationValidatorTest`, кейсы
`AssessmentServiceTest` с пробегом 96 000 км) не меняются. Feature-тесты не
добавляются: каталог `tests/Feature` пуст намеренно, первые пишет ДЗ.1.

## Риски

- **Столкновение с `max_mileage_km`.** В секции `vehicle` окажутся два mileage-порога с разной семантикой: 500 000 — потолок *валидации* (нарушение → 422, заявка вообще не доходит до решения), 400 000 — порог *решения* (> порога → `review`). Главный риск реализации — «выровнять» валидатор под 400 000: тогда заявки 400 001–500 000 начнут получать 422 вместо `review`, зона действия правила исчезнет, сломается сообщение валидатора и его тесты. `max_mileage_km` и проверка `ApplicationValidator.php:43–46` не меняются вообще.
- **Перезапись `reject` → `review` смягчает решение.** Буквальное прочтение задачи («иначе решение review») превращает отказ по LTV в ручной разбор только из-за пробега; механизма приоритета правил в коде нет, выбор приоритета — решение риск-менеджмента (AGENTS.md: не решать за человека). План закладывает буквальный вариант; альтернатива «худшее решение важнее» — точечное изменение условия в шаге 3 (понижать только `approve` → `review`) плюс правка соответствующего теста.
- **Смена сигнатуры конструктора `AssessmentService`.** Мест создания ровно два: `AppFactory.php:30` и `AssessmentServiceTest.php:24` (проверено поиском). Забыть `AppFactory` — runtime-ошибка на всех эндпоинтах; забыть `setUp()` — красный unit-сьют.
- **Границы.** «Не больше 400 000» реализовано строгим `>`: ровно 400 000 не срабатывает. Если заказчик имел в виду обратное — меняется знак сравнения и два теста.
- **`approved_limit`.** Правило никогда не даёт `approve`, поэтому при срабатывании лимит = 0 за счёт существующей логики; риск — случайно добавить свой расчёт лимита.
- **Сохранённые заявки.** Решение считается только в момент `assess()`; уже сохранённые заявки (включая seed) не пересчитываются — список и карточка продолжат отдавать старые решения. Для seed-заявок с пробегом 400 001–500 000 это расхождение с новым правилом, оно осознанное.
- **Соседнее, но чужое:** расхождение комментария и кода по границе `approve` (`<` vs `<=`, `DecisionEngine.php:10/32`) и справочник `ltv_by_age` (задача LOAN-12) — в задачу не входят, не трогать.
- **Пороги, лимиты и формулы не меняются ради зелёного `make test`** — при таком конфликте стоп и вопрос человеку (AGENTS.md).

Не входит в задачу: расчёт лимита по `ltv_by_age` (LOAN-12); фронтенд (форма уже
шлёт `mileage`, решение рендерится из ответа API); БД (`schema.sql`, `seed.sql`),
репозиторий и контроллер (контракт ответа не меняется: `decision` остаётся одной
из трёх строк); причины `review` в ответе API; пересчёт решений существующих
заявок; feature-тесты; изменение `max_mileage_km` и порогов LTV.

## Вопросы, на которые без заказчика не ответить

1. Приоритет правил: LTV говорит `reject`, пробег > 400 000 — итог `review` (буквальное прочтение задачи) или `reject` остаётся (`review` только вместо `approve`)? План закладывает буквальный вариант; это решение риск-менеджмента, в коде механизма приоритета нет.
2. Граница: ровно 400 000 км — допустимо (порог срабатывает с 400 001)? План предполагает «да» по формулировке «не больше».
3. «Пустой пробег» — подтвердить, что это по-прежнему ошибка валидации (422, решение не считается), а не `review`? Сейчас именно так; тест это фиксирует.
4. Нужны ли в ответе API причины решения (например, «review из-за пробега»)? Поля `reasons` в контракте нет — в план не включено.
5. Пересчитывать ли решения уже сохранённых заявок с пробегом 400 001–500 000 (в том числе seed)? План — нет, правило действует только на новые оценки.
6. Имя нового ключа конфига `vehicle.review_mileage_km` — согласовать? (Техническая мелочь, но ключ попадает в публичную конфигурацию правил.)
