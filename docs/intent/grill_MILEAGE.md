## Вопрос 1 из 4: приоритет правил (reject vs review)

**Вопрос.** Пробег > 400 000 км, при этом LTV в зоне `reject` (LTV > 85) — итоговое решение? Формулировку «иначе решение review» можно читать как безусловную перезапись любого вердикта, а можно как «пробег понижает только approve, reject важнее». Механизма приоритета правил в коде нет, решение риск-менеджмента (AGENTS.md).

- Вариант A: `review` перекрывает `reject` — буквальное прочтение, дефолт plan_MILEAGE.md
- Вариант B: `reject` остаётся — правило понижает до `review` только `approve`

**Ответ: review перекрывает reject.** Дефолт плана подтверждён; тест plan_MILEAGE.md:52 («400001 км, LTV 95 → `review`») остаётся без изменений.

## Вопрос 2 из 4: граница срабатывания

**Вопрос.** Ровно 400 000 км — порог срабатывает или нет? Спрошено явно, а не взято из формулировки автоматически: в этом коде уже есть расхождение по границе (комментарий `DecisionEngine.php:10` говорит `<= approve_max → approve`, код в `DecisionEngine.php:32` использует строгое `<`).

- Вариант A: 400 000 проходит, правило срабатывает с 400 001 (строгое `>`, стиль валидатора) — дефолт
- Вариант B: 400 000 уже даёт `review` (сравнение `>=`)

**Ответ: 400 000 проходит.** Строгое `>`, зона срабатывания — 400 001–500 000 км.

## Вопрос 3 из 4: причины решения в ответе API

**Вопрос.** Добавлять ли поле `reasons` (например, «review из-за пробега») в контракт ответа? Поля `reasons` в контракте нет, клиент видит только `decision: approve|review|reject`.

- Вариант A: не добавлять — контракт ответа не меняется, дефолт
- Вариант B: добавить поле `reasons` — расширение контракта, задача перестаёт быть точечной

**Ответ: не добавлять.** `decision` остаётся одной из трёх строк; причину можно добавить позже отдельной задачей.

## Вопрос 4 из 4: сохранённые заявки

**Вопрос.** Пересчитывать ли решения уже сохранённых заявок с пробегом 400 001–500 000 (в том числе seed)? Решение рождается только в момент `assess()` и хранится в БД как есть; в seed есть заявки, противоречащие новому правилу.

- Вариант A: не пересчитывать — расхождение с seed осознанное, дефолт
- Вариант B: пересчитать — нужен механизм пересчёта/миграции, заметное расширение scope

**Ответ: не пересчитывать.** Правило действует только на новые оценки через `assess()`.

## Итог

Все четыре ответа подтвердили дефолты plan_MILEAGE.md — план корректировок не требует.
Задействовано 4 из 6 допустимых вопросов. Зафиксированные решения:

1. Граница: ровно 400 000 км допустимо, правило срабатывает с 400 001 (строгое `>`).
2. Приоритет: перезапись безусловная — `reject` по LTV при пробеге > 400 000 становится `review`.
3. Пробег не указан: без изменений — 422 на валидации, решение не считается.
4. Контракт ответа: поле `reasons` не добавляется.
5. Сохранённые заявки и seed не пересчитываются.

Границы задачи (подтверждены планом): `max_mileage_km = 500000`, пороги и формула LTV,
сигнатура `DecisionEngine::decide(float $ltv)` не меняются; фронтенд, БД, feature-тесты,
`ltv_by_age` (LOAN-12), фикс расхождения комментария и кода по границе approve — вне scope.
